# ORDER NOTE (Sage cube row): Sage-1ply cube measured 16.63 ms (Zen5) when
#   run immediately after the Sage-0ply rows' ~2 min of sustained single-core
#   load, vs 14.40 ms standalone (matching 2026-08-02) — a ~15% sensitivity
#   to preceding load with tight within-run CIs both times (both runs in the
#   raw log). Committed values are from the light-prior-load condition, the
#   same condition as every other row.
# SAGE CUBE IS FIXED-OVERHEAD-BOUND: its 0-ply cube call costs nearly as much
#   as its 1-ply one (26.95 vs 29.24 ms Zen3; 10.88 vs 14.40 Zen5) — the cube
#   machinery, not net evaluation depth, dominates (matches the self-play
#   finding that Sage's cubeful cost is cube-bound).
# CUBE-STATE NOTE: per-position cube states matter — measured directly
#   (3000 boards, Zen3, 1-ply cfevaluate): centered 0.409 ms vs owned-at-2
#   0.385 vs owned-at-4 0.337 (0-ply: 0.0045 vs 0.0025). Recube evaluations
#   are CHEAPER, so a constant-centered convention would overstate gnubg's
#   cube cost; the shared pool avoids the approximation.
# These are ISOLATED primitive costs: for cache-reusing engines (gnubg, Sage)
#   they overstate the amortized in-play cube cost — in real play the pre-roll
#   cube evaluation shares its lookahead leaves with the same turn's move
#   search and prior turns' analysis (gnubg self-play marginal cube cost at
#   1-ply is ~0.08 ms vs 0.44 ms here). The self-play table is the amortized
#   comparison; the two methodologies bracket real cost.
# Zen3->Zen5 ASYMMETRY (PureTD cube ~3.9x vs checker ~2.7x) is real, not an
#   artifact — verified by direct microbenchmark on idle boxes:
#   the cube op is a BATCH-2 forward (offer_double evaluates the no-double +
#   double-take perspectives in one 2-row batch, td_agent.offer_double), and
#   the bare batch-2 net forward measures 149us Zen3 vs 37us Zen5 = 4.0x
#   (small-batch GEMV is vector-width/overhead-bound: Zen5 has AVX-512 +
#   higher IPC + DDR5 bandwidth; Zen3 is AVX2 — Zen5 batch-1 and batch-2 cost
#   the SAME 37-38us, i.e. fully overhead-bound), while batch~20 checker
#   forwards ratio only 2.25x (GEMM-efficient on both) plus ~1.7x-scaling C
#   move-gen. Self-play attribution corroborates independently (0.214 vs
#   0.033 ms).
# Cross-check vs the self-play cubeful table: recombining PureTD's two clean
#   latencies at the self-play decision mix reproduces the self-play
#   wall-clock within noise (Zen3: 11542 checker x 0.412ms + 8347 cube x
#   0.201ms = 6.43s vs the run's 6.60s, 2.5%).
# Run-to-run: sub-0.25ms rows drift ~8-12% between sweeps on boost clock;
